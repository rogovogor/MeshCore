# Энергосбережение ESP32-компаньонов: план

План перевода ESP32-компаньонов на автоматический light sleep. Код пригоден для
публикации (`[OS]`), но требует ядра, собранного с `CONFIG_PM_ENABLE`, — поэтому
первый шаг сделан на своей сборке библиотек. Первая плата — Heltec v3.

Справочник по механике, сборке ядра и замерам — `docs/esp32-companion-power-saving.md`.

## Зачем — измеренные факты

Heltec v3, замер по USB через FNB58:

| Что | Ток | Следствие |
|---|---|---|
| Штатная сборка, приложение подключено | 123 мА | |
| Штатная сборка, приложение отключено, экран включён | 127 мА | приложение стоит ~4 мА, экран ~8.5 мА |
| Штатная сборка, экран выключен | 118.5 мА | базу делают CPU на 80 МГц и непрерывный приём |
| Штатная сборка, отправка | ~250 мА | импульс TX, нормально |
| **С light sleep**, экран выключен, приложение подключено | **19–106 мА, пульсирует** | минимум совпал с замером форка (19.6 мА) |
| С light sleep, отправка | ~150 мА | |

Ток пульсирует: 19 мА — CPU спит, всплески — периоды бодрствования на события
BLE и приём LoRa. Сообщения при этом приходят и уходят, приложение подключается
и работает (в логе — `onConnect`, успешная авторизация, MTU 176, обмен кадрами).

## Что сделано

- код: `isReadBusy()` в базовом интерфейсе и в ESP32 BLE, `esp_pm_configure`/`esp_bt_sleep_enable` в `setup()`, уступка 10 мс в холостом цикле, отключение light sleep для USB-CDC/USB-компаньонов/WiFi; всё под `WITH_ESP32_POWER_SAVING`, по умолчанию выключено;
- окружение `Heltec_v3_companion_radio_ble_ps` с нашим ядром;
- путь к ядру через переменную `PS_FRAMEWORK`;
- переменная несёт спецификацию пакета целиком.

Ядро собрано: arduino-esp32 2.0.17 + IDF 4.4.7, дельта к штатному `sdkconfig`
(PM + тиклесс + BT modem sleep), `libesp_pm.a` 171 180 → 203 440 байт.

Проверено на железе: сборка и прошивка Heltec v3 (COM10) проходят, в логе
`ESP32 PM: 80-40 MHz, light sleep on`, приложение подключается.

## Целевые платы

Запрошены BLE-компаньоны на Heltec E213, E290, Wireless Tracker и v4.

| Плата | Вариант памяти | Нативный USB | `Serial` и признак хоста | Особенности |
|---|---|---|---|---|
| Heltec v3 (готово) | `qio_qspi` | нет (CP2102) | — | — |
| Heltec v4 | `qio_qspi` | да, режим 1 | `HWCDC`, `Serial.isConnected()` | FEM (PA/LNA), GPS |
| Wireless Tracker | `qio_qspi` | да, режим 1 | `HWCDC`, `Serial.isConnected()` | GPS |
| Heltec E213 | `qio_opi` | да, режим 0 | `USBCDC`, `(bool)Serial` | e-ink |
| Heltec E290 | `qio_opi` | да, режим 0 | `USBCDC`, `(bool)Serial` | e-ink |

Ядро собрано со **всеми шестью** вариантами памяти (`qio_qspi`, `qio_opi`,
`dio_qspi`, `dio_opi`, `opi_opi`, `opi_qspi`) — по памяти вопрос закрыт для всего
парка ESP32.

**Про USB — решено.** У этих плат `Serial` идёт через собственную USB-периферию
ESP32-S3 (у v3 между чипом и кабелем стоит CP2102, поэтому там проблемы нет), и
автоматический light sleep роняет эту линию. Но транспорт здесь **BLE**: порт
нужен только для лога и CLI, а нода живёт на батарее без кабеля. Поэтому сон
разрешён по умолчанию, а консоль защищают две вещи:

- **автодетект хоста** — пока хост на линии, держится блокировка
  `ESP_PM_NO_LIGHT_SLEEP` (у v4/Tracker — `HWCDC`, у E213/E290 — `USBCDC`);
- **окно по кнопке** — нажатие `PIN_USER_BTN` (активна в ноль) держит CPU бодрым
  30 секунд. Это запасной путь, если детект не сработал, и способ войти, когда
  кабель воткнули в спящую ноду: USB не будит CPU, но события BLE и приём LoRa
  будят его постоянно, поэтому нажатие замечается почти сразу.

Флаг `WITH_ESP32_POWER_SAVING_USB_SERIAL_SAFE` возвращает консервативное правило
(на таких платах не спать вовсе) — как в форке на PS 17.1.5.

Отдельно, чего в нашем дереве нет и что остаётся за рамками: экономия FEM LNA на
v4 (`radio.fem.rxgain off`, до 7.8–10 мА) и GPS-сон на v4 и Tracker. На E213/E290
не задана частота CPU — статические 80 МГц вместо 240 дадут заметную экономию.

## Настройка вместо флага

Профиль энергосбережения вынесен в настройки ноды: `set power.mode
auto|off|conservative|aggressive` и `get power`, плюс прежние `powersaving on|off`
как синонимы `auto`/`off`. Применяется на ходу, без перезагрузки; на nRF52 профиль
уважается так же. Хранится ключом `pwr_mode`, поэтому старые и новые прошивки
совместимы в обе стороны.

**Проверено на железе** (Heltec v3). В логе загрузки —
`ESP32 PM: 80-40 MHz, light sleep on, mode 0`: профиль читается из префов. Смена
профиля из CLI приложения применяется сразу, без перезагрузки:

```
ESP32 PM: 80-40 MHz, light sleep on, mode 3     <- set power.mode aggressive
ESP32 PM: 80-40 MHz, light sleep off, mode 1    <- set power.mode off
ESP32 PM: 80-40 MHz, light sleep on, mode 0     <- set power.mode auto
```

## Собранные прошивки

Готовые образы для десяти окружений (наше ядро,
`WITH_ESP32_POWER_SAVING=1`, с настройкой профиля): E213, E213 screen_180, E290, E290 screen_180,
Wireless Tracker, v4, v4 tft, v4 r8, v4 r8 tft — по два файла на плату (полный
`merged.bin` для прошивки в `0x0` и `app.bin` для обновления приложения).

Имя файла: `<плата>[_<вариант>]_ble_ps_<дата>_<билд>_<вид>.bin`. Лежат с
инструкцией рядом с образами (вне репозитория).

Ревизии v4: **V4.2 (GC1109) и V4.3 (KCT8103L) покрывает одна сборка** — тип FEM
определяется автоматически (`variants/heltec_v4/LoRaFEMControl.cpp`). «V4 R8» —
отдельная плата (8 МБ PSRAM), для неё отдельные сборки. **V4.1 в дереве нет**:
ни варианта, ни упоминания, нужно выяснять отличия от V4.2.

## Осталось

1. **Проверка на железе** четырёх плат: прошивка готовыми образами, замер и
   проверка, что консоль по USB остаётся рабочей. Ни одна из них ещё не
   прошивалась.
2. **Средние значения за окно** на v3 (с приложением и без) — по ним судить об
   эффекте, а не по диапазону.
3. **Параметры BLE-соединения** — отдельный процесс тюнинга: интервал 15–30 мс и
   slave latency 4 задают частоту пробуждений.
4. **RXPS** — аппаратный duty-cycle приёма, усыпляет само радио; в апстриме его
   нет, только в форке.
5. **Необязательные компоненты ядра** (камера, esp-dsp, esp-sr, esp-dl, littlefs):
   сейчас их библиотеки взяты из штатного пакета.
6. **Публикация.** Ветка и ядро пока локальные: ядро — релизным артефактом, затем
   перенос `[OS]`-кода в публичную линию вместе с инструкцией по сборке ядра.

## Ограничения, о которых помнить

- На Windows `file:///C:/...tar.gz` в `platform_packages` не работает: PlatformIO
  принимает архив за каталог. Рабочий путь — распаковать пакет поверх
  `%USERPROFILE%\.platformio\packages\framework-arduinoespressif32` и убрать
  `platform_packages` из окружения.
- Наше ядро встаёт **на место штатного**: пока оно установлено, все ESP32-сборки
  на этой машине линкуются с PM. Само по себе это ничего не меняет (PM включается
  только вызовом `esp_pm_configure`, а его делает лишь код под флагом), но помнить
  надо. Вернуть штатное — удалить каталог пакета.
- Сборка с нативным USB-CDC, USB-компаньоном или WiFi **намеренно** получает
  только частотное масштабирование: light sleep им противопоказан.
